# منصة وسايل — Wasayel Platform

منصة تجارة وخدمات **متعددة المستأجرين، عربية أولاً**: المستأجر الواحد = تطبيق
كامل بهويته وأدواره وفئاته (سوق، إيجار عقاري، مشاوير تفاوضية، خدمات، سكن
مشترك)، يُبنى **بالتهيئة لا بالكود**، ويُهيّأ جزئياً عبر وكيل استوديو ذكي
مقيد الأدوات يعمل باعتماد بشري.

**المكدس**: ‎.NET 10 + ASP.NET Core + Blazor Server، و**Marten 9**
(مخزن أحداث + وثائق فوق Postgres بعزل مستأجرين تلقائي — conjoined tenancy)،
و**Wolverine 6** (وسيط + نقاط HTTP بدوال static بلا Controllers).

> **النسب**: هذا المستودع مستخرج بتاريخه الكامل من المستودع الأم
> `acommerce-lab/acommerce-platform` (مجلد `platform-v1`)، ثم زومن مع حالة
> النشر `deploy-hf`. منهجيات الحقبة السابقة (نموذج OAM) محفوظة في
> [docs/heritage](docs/heritage/README.md).

## تشغيل سريع

Windows (PowerShell كمسؤول):

```powershell
.\scripts\setup-windows.ps1   # مرة واحدة: .NET + Postgres + قاعدة البيانات
.\scripts\run.ps1             # في كل تشغيل
```

Linux / macOS: `./scripts/run.sh` (يفترض Postgres مشغلاً — راجع INSTALL.md).

الرابط: http://localhost:5050

## الحالة — بصدق

**فعلي ويعمل**: العُدد الـ24، خط الصفقات الموحد بواجهاته (stepper + سجل زمني
+ إجراءات)، تذاكر الدعم بالرد والإغلاق، إشراف الإعلانات، التقييمات المتبادلة
المربوطة بالصفقات، وكيل الاستوديو (Anthropic/Gemini/OpenAI)، PWA لكل دور.

**Mock بمنافذ جاهزة للتبديل**: OTP بقناتيه — الهاتف (MockSms) والبريد
(MockEmail) — كلاهما يطبع رمزاً ثابتاً `123456` في اللوغ ولا يرسل شيئاً،
وهو الافتراضي التطويري؛ نفاذ (MockNafath)، الدفع (MockPaymentProvider —
فواتير بهيئة ZATCA وVAT ‏15% وidempotency keys)، التوصيل (دورة شحنة كاملة
على مؤقت)، الخرائط.

**بُني حديثاً (2026-08-09)**: مشروع اختبارات `tests/ACommerce.Platform.Tests`
(xUnit — توصيف `DealsPolicy` كبذرة T5/T6 + اختبارات مصادقة المخطط كبذرة T3)
مع بوابة CI على GitHub Actions، وبوابة تحقق رسمي بمخطط JSON
(`AgentToolValidator`) تُفرض أولاً في منفذ أدوات الوكيل. العدد يومَها
**216 اختباراً** خضراء (‏179 + ‏18 لحلّ جلسة الدور + ‏19 لتعدد الأدوار
وإصلاح الـ403، انظر أدناه) — والعدد اليوم **326** (انظر الفقرات التالية).

**وكلاء الذكاء الاصطناعي بملفّات تعريف مسمّاة (2026-08-10)**: كان الوكيلان
المنطقيان — **التحليل** (`FeasibilityAnalysisService`، دراسة الجدوى) و
**الاستوديو** (`AgentService`، أدوات المستأجرين) — يتقاسمان `IAgentBackend`
واحداً singleton ومفتاحاً واحداً، وكانت قراءة `Agent:ApiKey` مكرّرة في
الخلفيات الثلاث بسقوط بيئة مختلف لكلٍّ. الآن لكلّ وكيل **ملفّ تعريف مستقلّ**
(`AgentProfile`: مزوّد + عنوان + مفتاح + نموذج + تسمية) يُحلّ بقاعدة سقوط
واحدة في موضع واحد — `Agents:{Name}:{Key}` ← `Agent:{Key}` القديم ←
متغيّر البيئة — ويُبنى عبر `IAgentBackendProvider.For("Studio"|"Analysis")`
بتسجيل DI واحد. الخلفيات الثلاث صارت **خيارات-صِرفة** لا ترى `IConfiguration`.
الغرض التشغيلي: نموذج ذكيّ للتحليل وأخفّ للاستوديو على GitHub Models المجّاني
(مثال التهيئة الثنائية في [AGENT-TOOLS §1](docs/AGENT-TOOLS.md)). **التوافق
الرجعي مبرهن لا مُدَّعى**: تهيئة `Agent:*` وحدها تعطي الوكيلين **نفس كائن
الخلفية بعينه** بنفس المزوّد والمفتاح والنموذج — توصيف بـ`Assert.Same` ضمن
**48 اختباراً جديداً** (‏217 ← **265**). وأُصلح بالمناسبة انحرافان صامتان:
وكيل التحليل كان يستخدم `DefaultModel` العارية فيتجاهل تهيئة نموذجه، و
`"Model": ""` الحشو في `appsettings.json` كان يُرسَل نموذجاً فارغاً ويحجب
سقوط متغيّر البيئة — والفارغ الآن يُعامَل «غير مضبوط». **حدّ معلن**: لا مفتاح
GitHub Models في هذه الموجة، فالتحقق حيّ لم يجرِ — الاختبارات كلها على طبقة
الحلّ والتكوين بلا نداء LLM واحد.

**سياسة الصفقات صارت بيانات (2026-08-09 — الخطوة 4 من البروتوكول)**: الأنماط
الخمسة خرجت من `switch` مُجمّع إلى كاتالوج بيانات في موضع واحد
(`Services/Deals/DealPatternCatalog.cs`) فوق سجل `DealPatternDefinition`
(اسم النمط + صفوف مراحل، كل صف يحمل مرحلته وفاعلها وتسميتها). واجهة
`DealsPolicy` العامة لم تتغير حرفاً — `StagesFor`/`Next`/`Actor`/`LabelAr`
بتواقيعها — فلا مستهلك واحد احتاج تعديلاً و`DealsService` لم يُمس.
**برهان التطابق** لا الادعاء: اختبار توصيف يلتقط السلوك كاملاً (التسلسل
لكل نمط من الستة، و`Next` لكل مرحلة من الثمان لا لمراحل النمط فقط،
و`Actor`/`LabelAr` للقيم الثمان) كُتب واخضرّ **قبل** الرفع في كوميت مستقل،
ولم يُمس سطر منه بعده. ومعه بوابة T5/T6 كدوال نقية
(`DealPatternValidator`): الأنماط الخمسة تجتازها، وأنماط فاسدة مصطنعة
(بلا `Offered` في البداية، بتكرار يصنع دورة، بفاعل خارج الأربعة، بمرحلة
خارج التعداد) تُرفض برمز الخرق المقصود. **حدّ معلن**: الكاتالوج **في
الكود** لا في Marten — لا تخزين لكل مستأجر في هذه الموجة؛ الشكل مصمم له
(وثيقة لكل نمط) وحين يُنفّذ يتغير `DealPatternCatalog.For` وحده.

**الأدوار صارت ملفات (2026-08-10 — الموجة الأولى)**: القوالب السبعة
(`customer · rider · vendor · driver · host · shipper · tenant_admin`)
خرجت من مصفوفة `RoleTemplate` مجمَّعة داخل `RoleCatalog.cs` إلى **ملف
JSON لكل دور** —
`libs/kits/Roles/ACommerce.Kit.Roles.Core/Definitions/{slug}.role.json`
بترتيب `roles.index.json`. الملفات ظاهرة في المستودع (تُقرأ وتُحرَّر
ويظهر فرقها في الـ diff) ومضمونة في التجميع عند النشر، بلا سقوط بين
مصدرين — لأن مصدرين للحقيقة هما الانحراف الصامت الذي جاءت الموجة
لتزيله. واجهة `RoleCatalog` العامة لم تتغير حرفاً (`All`/`Find`/
`InstantiateRole`) فلا مستهلك واحد من التسعة احتاج تعديلاً.
**برهان التطابق** لا الادعاء: توصيف يلتقط سطح الكاتالوج كاملاً — كل
خاصية لكل قالب، والصلاحيات **بترتيبها**، والحقول بأنواعها وخياراتها
**بنصوصها المشكولة حرفياً**، ومصفوفة `RolePermissions.Has` كاملة —
كُتب واخضرّ في كوميت مستقل **قبل** النقل ولم يُمس سطر منه بعده.
ومعه ثلاثة مكاسب جديدة: **معجم صلاحيات مغلق** (`PermissionCatalog` —
ثماني صلاحيات موثقة أول مرة، ومفصولة صراحة عن أسماء إجراءات سجل
التدقيق التي تشبهها شكلاً)، و**حاويات توطين** لكل سلسلة يراها المستخدم
(`{ar, en}` — العربية مملوءة بتشكيلها والإنجليزية بنية جاهزة فارغة)،
و**مصادق** (`RoleDefinitionValidator`) بدوال نقية ورموز خرق ثابتة
مفروض **بوابةً عند التحميل**: تعريف فاسد يُفشل الإقلاع باسمه ورمزه.
الاختبارات **265 ← 309**. **حدود معلنة**: القراءة تبقى العربية كما اليوم
(خدمة التوطين وزر اللغة لم يُربطا)، و**التصيير لا يقرأ قسم `composition`
بعد** — يتفرّع كما كان بـ `switch` على `CatalogSlug`؛ قيمة القسم آنذاك
توثيق التركيب ومصادقة المعجم وجاهزية الموجة الثانية. **وهذا الحدّ الأخير
رُفع في الموجة الثانية أدناه.** التفصيل في
[META-MODEL §6](docs/META-MODEL.md).

**التصيير صار يقرأ الملفات (2026-08-10 — الموجة الثانية)**: قرار «أي
رئيسية/نموذج إنشاء/شريط تنقل/وضع استكشاف لأي دور» كان منثوراً في ستة
مواضع تصيير، كل واحد يتفرّع بنفسه على اسم الدور. صار الآن يُقرأ من قسم
`composition` في ملف تعريف الدور، عبر **نقطة قلب واحدة**
(`RoleCompositionResolver.Resolve`) وقاموس مغلق في كل موضع يحوّل القيمة
المعجمية إلى مندوب تصيير — **لا انعكاس على أسماء حرة**، ومع سقوط آمن
وسطر تحذير لقيمة غير مسجَّلة. ومعه رُفع `PatternFromTenant` إلى بيانات:
شروطه التي كانت تذكر أسماء أدوار بأعيانها صارت حقل `dealPatternAffinity`
في ملف كل دور، وترتيب غلبة معلن (`trip` قبل `rental`) — فإضافة دور يجرّ
نمطاً لم تعد تمسّ كوداً. **برهان التطابق ثلاثي**: توصيف كُتب واخضرّ على
الـ `switch` **قبل** التبديل في كوميت مستقل ولم يُمس سطر منه بعده، ثم
اخضرّ على القراءة من الملفات؛ و**عشرون صفحة مرجعية** ملتقطة بـ curl قبل
وبعد **متطابقة بايتاً ببايت**. الاختبارات **309 ← 315**. **حدود معلنة**:
`publicProfile` تبقى توثيقاً لا حراسة (لا بوابة دور في `VendorProfile`
أصلاً)، و`roleHomeHero` يبقى يتيماً بقرار. التفصيل في
[META-MODEL §6.3](docs/META-MODEL.md).

**دور جديد صار ملفاً فقط (2026-08-10 — الموجة الثالثة)**: الموجتان
السابقتان نقلتا الأدوار السبعة إلى ملفات وجعلتا التصيير يقرؤها. هذه
الموجة **تختبر الدعوى**: أُلِّفت ثلاثة أدوار جديدة — `broker` (وَسيط)
و`mover` (ناقِل أَثاث) و`organizer` (مُنَظِّم فَعالِيّات) — **ملفات JSON
خالصة، بلا سطر C# واحد** في التصيير أو التنقل أو تعداد الوكيل. الكاتالوج
**سبعة ← عشرة**.

والدليل حيّ لا وحدوي فقط: مستأجر تجريبي أُنشئ من مسار الإدارة القائم،
فُعّلت عليه الثلاثة + `customer`، ودخول MockNafath بكل دور أعطى — **بلا
تعديل كود** — رئيسيةَ الدور وشريطَ تنقّله ووضعَ استكشافه من قسم
`composition`، وشاشةَ onboarding بحقوله وخيارات `SingleSelect` من قسم
`fields`، ومختصراتِ PWA بما فيها `extras` (‏`driverArea` لـ`mover`،
و`driversList` لـ`organizer`). وانجذاب `mover` إلى `trip` ظهر **أثراً
مرئياً**: صفحة الإعلان تعرض تدفّق الصفقة بخمس مراحل (نمط `trip`) بينما
مستأجر شاهد بالتركيبة نفسها **بلا** `mover` يعرض سبعاً (`marketplace`) —
والمتغيّر الوحيد سطرٌ في ملف.

ومعها وُحِّد مصدر ثالث: تعداد `set_roles` في `AgentService` كان مكتوباً
يدوياً في ثلاثة مواضع (مخطَّط + وصف + تعليق) وكان التعليق **ناقصاً
`rider`** فعلاً — صار الثلاثة تُشتق من `RoleCatalog.All`، فالأدوار
الثلاثة دخلت تعداد الوكيل وبوابة `AgentToolValidator` بلا لمس.
**والتوصيف تطوّر ولم يتآكل**: كل سطر من أسطر السبعة بقي نصّاً كما هو،
والتغيير الوحيد غير المُلحَق هو سطر العضوية في `[order]` — ‏107 أسطر
مضافة وسطر واحد معدَّل وصفر محذوف في توصيف الكاتالوج، و‏31 مضافة وصفر
معدَّل في توصيف التصيير، مقيسة بـ`diff`. وصفحات `ashare` الخمس (البوابة
+ رئيسيات أدواره الثلاثة + `explore`) **متطابقة بايتاً ببايت** قبل وبعد.
الاختبارات **315 ← 326**. **الحدّ الصادق**: «بلا كود» صحيحة، **و«بلا
إعادة بناء» ليست بعد** — الملفات موارد مضمونة، فإضافة دور تعني ملفاً +
سطر فهرس + إعادة بناء؛ ما سقط كتابةُ الكود لا دورةُ النشر، وإسقاطها هو
موجة Marten القادمة. الخطوات العملية في
[META-MODEL §6.6](docs/META-MODEL.md).

**قناة مصادقة بالبريد (2026-08-09)**: قيمة ثالثة لقناة المستأجر إلى جانب
`phone` و`nafath`. آلية الرمز **هي نفسها** (نفس التوليد والتجزئة ومهلة
العشر دقائق وحدود المعدل في `AuthHandlers`) — الجديد هو المُرسَل إليه
والمزود. مزودان: `Auth.Providers.MockEmail` (الافتراضي، تطويري، لا إرسال
فعلي) و`Auth.Providers.Smtp` (فعلي عبر MailKit، يعمل مع أي SMTP بما فيه
Azure Communication Services). التبديل بسطر تهيئة واحد:
`Auth:Email:Provider=smtp` مع `Auth:Email:Host/Port/Username/Password/From`
— **لا سرّ في الكود**، وبلا هذه التهيئة يبقى Mock عاملاً. الحالة بدقة:
المسار كامل من الواجهة إلى تخزين المستخدم ومختبَر منطقياً بلا قاعدة
بيانات، لكن **لم يُرسَل بريد فعلي عبر SMTP بعد** — راجع
[PRODUCTION-PLAN](docs/PRODUCTION-PLAN.md) لما يلزم لتفعيله إنتاجياً
(نطاق مُصادَق SPF/DKIM/DMARC واعتماد مزود وسمعة إرسال).

**وضوح وتحفيز وSEO (2026-08-09)**: ثلاث إضافات عرضية لا تمس خط الصفقات
ولا دلالته التشغيلية — `DealsPolicy` و`DealsService` والأحداث ومخططات أدوات
الوكيل بلا تغيير حرف واحد.

- **شرح التدفق** (`Components/FlowExplainer.razor`): خط زمني يبين مراحل
  الصفقة ومن يحرك كل مرحلة، **مشتق بالكامل** من `DealsPolicy.StagesFor`
  و`LabelAr` و`Actor` — لا نص مرحلة منسوخ، فتغيير السياسة يغير الشرح
  تلقائياً. مطوي في صفحة الإعلان، ومفتوح فوق الـ stepper في صفحة الصفقة.
- **«دورك الآن»** (`Services/Ux/DealTurnView.cs`): بطاقة تخبر المستخدم
  الحالي تحديداً هل الإجراء التالي منه، مبنية على **نفس** قاعدة الفاعل التي
  يفرضها `DealsService.AdvanceAsync` — واختبار يقارن الاثنتين عبر كل نمط
  وكل مرحلة، فلا تعد الواجهة بما يرفضه المحرك. مع حالات فارغة موجهة (كل
  قائمة فارغة صار لها خطوة تالية واحدة) ومؤشرات ثقة (مُوثَّق/مميَّز وعدد
  تقييمات المعلن) بألوان العلامة من المستأجر.
- **SEO** (`Kit.Tenants.Core/Seo.cs` + `Kit.Tenants.Server/SeoHandlers.cs`):
  ترويسة ديناميكية لكل مستأجر (عنوان + وصف + canonical + theme-color +
  OpenGraph/Twitter) تُبنى من وثيقة المستأجر التي حمّلها الـ middleware
  أصلاً — صفر استعلام إضافي؛ و JSON-LD (`Organization` + `WebSite`)
  للرئيسية؛ و`robots.txt` و`sitemap.xml` كنقطتي Wolverine HTTP تستثنيان
  `_admin` والمستأجرين المعلقين ومسارات الإدارة والاستوديو. **دوال البناء
  نقية** (بلا قاعدة بيانات) ومختبرة كذلك. الصفحات العامة كانت — وبقيت —
  SSR ثابتاً بالكامل (لا `@rendermode` إلا في صفحتي وكيل)، فالزاحف يستلم
  HTML مكتملاً بلا انتظار SignalR.

**عطل مُصرِّف Wolverine — أُصلح**: بعد ترقية Wolverine إلى 6 (`b8efc91a`) لم
يعد الـ core يشحن مُصرِّف وقت التشغيل، فكان `WolverineRuntime.StartAsync` يرمي
`TypeLoadMode.Dynamic ... no IAssemblyGenerator (Roslyn) is registered` قبل
خدمة أي طلب. العلاج المعتمد: حزمة `WolverineFx.RuntimeCompilation` ‏6.25.1
(مطابقة لبقية حزم Wolverine) في `Directory.Packages.props`، ومرجعها في
`ACommerce.Platform.Hosting` — حيث يُستدعى `UseWolverine` — مع نداء صريح
`opts.UseRuntimeCompilation()`؛ الحزمة تُسجِّل نفسها تلقائياً والنداء
idempotent، وذِكره يجعل الاعتماد ظاهراً في الكود لا مُضمَراً. التحقق: نسخة
مصغرة معزولة بنفس الحزم ترمي الاستثناء نصّاً قبل الإصلاح، وبعده يمضي التوليد
ويكون الفشل التالي `Npgsql: Failed to connect to 127.0.0.1:5432` فقط؛
و`V1.App.deps.json` صار يحمل `WolverineFx.RuntimeCompilation/6.25.1` و
`JasperFx.RuntimeCompiler/5.0.0` و`Microsoft.CodeAnalysis`. البديل للإنتاج
(توليد مسبق `dotnet run -- codegen write` مع `TypeLoadMode.Static` وشحن بلا
Roslyn) يبقى مفتوحاً متى لزم تصغير الحزمة وتسريع الإقلاع البارد.

**عطل مولّد Marten المصدريّ — أُصلح**: مستقلّ عن سابقه وسابقٌ له في الترتيب،
فكان يقع في `AddPlatformHost` عند `AddMarten` قبل أن يعمل Wolverine أصلاً —
ولذلك كان يحجبه، ولم ينكشف إلّا برفع الأول. بعد ترقية Marten إلى 9 صار توزيع
دوال `Apply/Create` يتمّ بمولّد مصدر وقت التصريف بلا احتياطيّ وقت تشغيل،
فكان يرمي `InvalidProjectionException: No source-generated dispatcher found
for SingleStreamProjection<Listing>`. السبب: مشاريع الـ Core التي تُعرَّف فيها
التجميعات الأربع (`Listings`, `Subscriptions`, `Support`, `Offers`) كانت
ملفّات مشروع عارية بلا أيّ `PackageReference`، والمولّد يشحن داخل حزمة Marten
فلا يعمل في تجميعة لا تُشير إليها. العلاج: `<PackageReference Include="Marten" />`
في المشاريع الأربعة (بلا `Version` — الإدارة مركزيّة). المرجع وحده كفى: لم
تُمَسّ تصريحات الأنواع ولا احتاج أيٌّ منها `partial`، مصداقاً لنصّ الاستثناء
نفسه بأنّ النوع المسجَّل عبر `Snapshot<T>` لا يحتاجها.

التحقق: المولّد صار يبثّ `{Aggregate}Evolver` لكلّ تجميعة من الأربع — يغطّي
سبعة أحداث في حالة `Listing` — والتجميعات المبنيّة تحمل السمة
`[assembly: GeneratedEvolver]`. و`V1.App` صار يعبر `AddMarten` فعلاً ويمضي
حتى `PlatformSeed`، فيتوقّف عند اتصال Postgres وحده
(`Failed to connect to 127.0.0.1:5432`) — وهو أقصى ما يبلغه جهاز بلا قاعدة
بيانات. **بهذا لم يبقَ في طريق الإقلاع عائقٌ معروف غير Postgres نفسه.**

**عطل جلسة الدور على المسارات العامة — أُصلح (2026-08-09)**: الدخول عبر
`/{slug}/r/{role}/login` كان يكتب كوكي الدور وحده
(`.acommerce.auth.{slug}.{role}`)، بينما **كل** نقاط الـ POST تقريباً مسجلة
على مسارات بلا `/r/{role}/` وكانت تقرأ الاسم العام `.acommerce.auth.{slug}`
حرفياً في ‏46 موضعاً متفرقاً. فالمستخدم يرى نفسه داخلاً والخادم يراه مجهولاً:
‏`POST /{slug}/listings/create` يرتد ‏302 إلى `login?returnUrl=…`، وتقديم
العرض من صفحة الإعلان يفشل صامتاً بإعادة رسم الصفحة بلا رسالة. والفئة
المصابة أوسع من الحالتين المبلَّغتين: `listings/{id}/offers` و`cart/*`
و`checkout/submit` و`deals/*` و`searches/*` و`me/*` و`chats/*` و`trips/*`
و`api/{slug}/push/subscribe` — وهذا الأخير كان فيه سقوط يدوي **ميت** أصلاً
لأن بادئة مساره `api` فتُرجع `ExtractRoleFromPath` عدماً دائماً.

**العلاج** — قاعدة واحدة في موضع واحد (`AuthSession.ResolveToken`) تمر منها
كل القراءات، فلا يبني أحد اسم كوكي بيده: مسار **بدور** → كوكي ذلك الدور
وحده بلا سقوط (عزل الأدوار يبقى كما صُمّم)؛ مسار **بلا دور** → الكوكي العام
ثم أي كوكي دور لنفس المستأجر يحمله المتصفح. ومعها كتابة نسخة عامة عند
الدخول بدور، فيصير الحل حتمياً للجلسات الجديدة والمسح لا يلزم. التوسيع آمن
لأن التوكن **لا يحمل دوراً** أصلاً (`{userId}|{tenantSlug}|{exp}|{sig}`)،
فكوكيز أدوار المستخدم الواحد متكافئة هوية، والتفويض يظل بعدها عبر
`RolePermissions.Has(tenant.Roles, user.ActiveRole, …)`.

**البرهان** لا الادعاء: ‏18 اختبار وحدة على نمطي المسار، منها خمسة على
مسارات POST الفعلية — سقطت ‏8 منها على السلوك القديم واخضرّت بعده؛ ثم
end-to-end على فرع Neon حيّ: دخول نفاذ بهوية `1000000009` بدور `host` →
‏`POST /ashare/listings/create` صار ‏302 إلى `/ashare/listings/{id}` بدل
`login`، والإعلان يظهر بعدها بـ GET. وأُعيد البرهان بجرة كوكيز **منزوع
منها الكوكي العام** (شكل الجلسة قبل الإصلاح بالضبط) فنجح كذلك. وضبط سالب
محفوظ: طلب بلا جلسة ما زال يرتد إلى `login`.

**عطلان في طبقة التفويض — أُصلحا (2026-08-09)**:

- **‏403 يصير 500 عند كل رفض صلاحية — أُصلح**: المنصة لا تستدعي
  `AddAuthentication` إطلاقاً، فكل `Results.Forbid()` كان يرمي
  `System.InvalidOperationException: Unable to find the required
  'IAuthenticationService' service` من `ForbidHttpResult.ExecuteAsync` →
  ‏500 بدل ‏403 لكل رفض في المنصة. برهان حيّ قبل الإصلاح: `POST
  /ashare/listings/create` بدور `customer` (لا يملك `listing.create`) أعطى
  ‏500 مع الاستثناء في جسم الرد (وضع التطوير). **العلاج**: استبدال أربع
  استدعاءات `Results.Forbid()` بردّ ‏403 لا يحتاج خدمة مصادقة —
  `PermissionFilter` (موضعان) بـ `Results.StatusCode(403)`، و`chats/{id}/send`
  و`admin/tenants/{slug}/suspend` بالمساعد القائم `Forbidden()` (نفس
  `StatusCode(403)`). `Results.Unauthorized()` (401) لا يحتاج الخدمة فبقي كما
  هو. برهان بعد الإصلاح: نفس الطلب صار ‏403 نظيفاً بلا استثناء في السجل.

- **تعدد الأدوار المتزامن — أُصلح**: `User.ActiveRole` حقل واحد مخزَّن؛
  المسارات المسوَّرة بدور تتفوق بالـURL، لكن **نقاط الكتابة بلا دور**
  (`listings/create` عبر `PermissionFilter`، و`listings/{id}/offers` عبر
  `HasPermissionAsync`) كانت تسقط إلى الحقل المشترك = آخر تسجيل دخول يفوز،
  فمستخدم بدورين على نفس المتجر لا يعمل بهما متزامنين. **العلاج**: دور فعّال
  صريح — النموذج على الصفحة المسوَّرة بدور يحمل `as=<الدور>` مخفياً، ونقطة
  الكتابة تحسم `effectiveRole = as (لمن يملكه) ← دور الـURL ← ActiveRole
  المخزَّن` في موضع واحد (`Gates/EffectiveRole.cs`)، **دون كتابة الحقل
  المشترك**. الأمان: `as` مجرد اختيار بين أدوار يملكها المستخدم فعلاً —
  المِلكية يثبتها وجود كوكي جلسة ذلك الدور لنفس المستخدم (نفس نموذج عزل
  الجلسات)، وقيمة `as` لدور غير مملوك **تُهمَل** فيسقط الحسم لدوره الحقيقي؛
  والتفويض يبقى `RolePermissions.Has`. **البرهان** — ‏19 اختبار وحدة (قرار
  نقيّ + برهان مِلكية بالكوكي + تركيب مع التفويض + اختيار ردّ الـ403)، ثم
  ثلاثة براهين curl حيّة على فرع Neon: (١) `customer` على `create` → ‏403؛
  (٢) نفس الجرّة، دخول `host` ثم `customer` (فـ`ActiveRole=customer`) ثم
  `create` بـ`as=host` → ‏302 للإعلان الجديد، وبـ`as=customer` أو بلا `as` →
  ‏403؛ (٣) ضبط سالب — `as=host` لمستخدم لا يملك كوكي host → ‏403 (لا يُخدع
  النظام بـ`as`).
