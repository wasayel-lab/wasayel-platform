# خطة الأدوار كتطبيقات فرعية — تصميم احترافي وسير عمل إنتاجي

> مُكمّلة لـ `PRODUCTION-PLAN.md` (الطبقة ٤).
> الهدف: كل دور = تطبيق ويب-تقدّمي مستقل بتصميم احترافي وسير عمل كامل
> قابل للإطلاق التجاري.

---

## المبادئ الموحّدة (تنطبق على كل القوالب)

### مبادئ التصميم

1. **Mobile-first فعلي** — كل شاشة تُصمَّم بافتراض هاتف 360px أولاً، الـ
   desktop يُعتبَر استثناءً. الـ thumb-zone (آخر ثلث الشاشة) هو المساحة
   النشطة للأزرار الأساسية.

2. **هرمية بصرية صارمة لكل شاشة**:
   - **عنوان (H1)**: ما هذه الشاشة. 22-26px.
   - **سياق (sub)**: لماذا أنت هنا الآن. 13-14px مكتوم.
   - **إجراء أساسي واحد** بارز ومُكرّر (في الـ hero + sticky-bottom على الجوال).
   - **خلاصة نشاط حية** (آخر N بطاقات قابلة للنقر).
   - **إجراءات ثانوية** خلف زر "المزيد" (overflow menu).

3. **حالات مصمّمة، ليست شاشات بيضاء**: لكل شاشة (loading skeleton مشابه
   للتخطيط، empty state بإيموجي + جملة سياقية + CTA، error state بسبب
   مفهوم + إعادة محاولة، success toast بعد الإجراء).

4. **التغذية الراجعة الفورية**: كل إجراء ينتج رد فعل بصري خلال 100ms
   (zhinghover/active state)، وتأكيد ضمن 1s (toast/redirect).

5. **اللون الوظيفي**: لون العلامة للإجراءات الأساسية فقط؛ رمادي للثانوية؛
   أخضر للنجاح؛ كهرماني للتنبيه؛ أحمر للحذف/الرفض. الحالات (status chips)
   تستخدم palette متماسك (pending=رمادي، active=أزرق، success=أخضر،
   warning=كهرماني، danger=أحمر).

6. **نظام تصميم موحّد** (تطوير `studio.css`):
   - tokens (لون/خط/مسافات/زوايا/ظلال).
   - مكوّنات أساسية: `<AcDataTable>`, `<AcDrawer>`, `<AcTabs>`,
     `<AcToast>`, `<AcConfirm>`, `<AcStatusChip>`, `<AcSparkline>`,
     `<AcEmpty>`, `<AcSkeleton>`, `<AcStickyBottomActions>`.
   - كل التطبيقات الفرعية تستخدم نفس المكوّنات (بألوان العلامة).

### مبادئ سير العمل

1. **state machine صريحة لكل entity** (مَطابقة Marten events). كل
   انتقال له شرط + إجراء + إشعار. لا "حالات معجزة" تظهر بدون event.

2. **التأكيد قبل الفعل المُكلِف** (حذف، إلغاء، قبول مالي). Modal تأكيد
   يذكر العواقب (مثلاً "سيُعاد دفع X ريال").

3. **سياق الدور دائماً ظاهر**: شارة الدور في الـ header، وأي إجراء يحتاج
   دوراً مختلفاً يقترح "بدّل الدور" بدلاً من فشل صامت.

4. **Real-time حيث يهم**: عروض واردة، رسائل جديدة، تغيّر حالة رحلة —
   تُدفع عبر SignalR (RealtimeHub موجود) لا polling.

5. **Onboarding تدريجي**: الحقول المطلوبة للدور (RoleField) تُجمع عند
   أول مرة يحتاجها العمل، لا قبلها (just-in-time).

## النمط ١ — Marketplace (متجر متعدد البائعين)

**أمثلة الإنتاج**: متجر ملابس، سوق إلكترونيات مُجدَّدَة، سوق منتجات حرفية.

### الحالة الحالية

- **SellerHome.razor** (host/vendor): بطاقة CTA "إعلان جديد" + شريط
  KPIs (نشط، مشاهدات، محادثات) + قائمة إعلاناتي. أساسي وغير كافٍ
  للإنتاج.
- **TenantHome (default branch)**: hero + بحث + فئات + مميّز + أحدث —
  هذا هو "تطبيق المشتري" حالياً. وظيفي لكن تجربة عادية.
- **Listing.Server موجود** (CreateListing/EditListing/DeleteListing/View).
- **Subscriptions.Server موجود** (Plan/Subscription + Quota).
- **مفقود**: Orders/Inquiries، Reviews، Payments، Analytics للبائع.

### تطبيق البائع — الشاشات المستهدفة

`/{slug}/r/vendor/...`

1. **لوحة البائع** (`/`):
   - KPI cards: مشاهدات ٧ أيام (sparkline)، رسائل جديدة، إعلانات نشطة،
     عروض/استفسارات معلّقة، تقييم متوسط (نجوم).
   - "يحتاج انتباهك": رسائل لم يُرَد عليها > 24h، إعلانات على وشك
     الانتهاء، مراجعات سلبية جديدة.
   - رسم خطي: مشاهدات/اتصالات/تحويلات ٣٠ يوم.

2. **إدارة الإعلانات** (`/me/listings`):
   - `<AcDataTable>`: عنوان، فئة، حالة (مسودة/نشط/متوقف/منتهي)، سعر،
     مشاهدات، استفسارات، تاريخ، إجراءات.
   - فلترة بالحالة/الفئة/المدينة، ترتيب، بحث، تحديد متعدد.
   - إجراءات جماعية: تفعيل/إيقاف/تجديد/حذف.
   - زر "إعلان جديد" sticky-top.

3. **إنشاء/تعديل إعلان** — wizard ٤ خطوات:
   - الأساسيات (عنوان، وصف، فئة)
   - الموقع (مدينة، حي، موقع جغرافي اختياري)
   - السعر والتفاصيل (حقول ديناميكية من DynamicAttributes حسب الفئة)
   - الصور (مفقود حالياً — يحتاج تخزين صور)
   - معاينة قبل النشر.

4. **تفاصيل إعلان واحد** (`/me/listings/{id}`):
   - معاينة كما يراها المشتري + KPIs الإعلان (مشاهدات يومية، استفسارات،
     مفضلة) + المحادثات المرتبطة + سجل التعديلات.

5. **الاستفسارات/الطلبات** (`/me/inquiries`):
   - **نطاق مفقود** — يحتاج بناء `Inquiries` kit أو استخدام Conversations
     كقناة + علم `IsInquiry`. لكل استفسار: المشتري، الإعلان، الرسالة
     الأولى، الحالة (جديد/رُدّ عليه/مُغلَق).

6. **المحادثات** (`/chats`): قائمة + غرفة محادثة (موجودة، تُصقَل).

7. **التقييمات** (`/me/reviews`):
   - **نطاق Reviews مفقود تماماً** — يحتاج بناء.
   - عرض المراجعات الواردة، الرد على مراجعة، شارة "موثّق" للمشتري الفعلي.

8. **التحليلات** (`/me/analytics`):
   - مشاهدات/اتصالات/تحويلات بمدى زمني قابل للاختيار.
   - أفضل الإعلانات أداءً، أبطأ الإعلانات، مصادر الزيارات (إن وُجد tracking).

9. **الباقة والمدفوعات** (`/me/plan`):
   - الباقة الحالية، الحصة المستخدَمة، تاريخ التجديد، الفواتير، طريقة الدفع.

### تطبيق المشتري — الشاشات المستهدفة

`/{slug}/...` (الدور default/customer)

1. **الرئيسية**: hero + بحث + فئات (موجود).
2. **استكشاف** (`/explore`): فلترة متقدمة (موجود، يحتاج صقل).
3. **تفاصيل إعلان** (`/listings/{id}`):
   - معرض صور (مفقود)، سعر، بائع، تقييماته، أزرار: محادثة، مفضلة،
     مشاركة، إبلاغ.
   - "إعلانات مشابهة" أسفل.
4. **مفضلة** (`/favorites`): موجود.
5. **بحوث محفوظة** (`/me/searches`): موجود.
6. **محادثاتي** (`/chats`): موجود.
7. **حسابي** (`/me`): تعديل بروفايل، طلباتي السابقة، تقييماتي.

### State machines

**Listing**: `draft → active → (paused | expired) → deleted`.
- `paused` يدوي من البائع، يخفيه من البحث.
- `expired` تلقائي بعد X يوم (من خطة الاشتراك).

**Inquiry** (نطاق جديد): `new → replied → resolved | closed`.

**Review** (نطاق جديد): `pending_verification → published | rejected`.

### الفجوات النطاقية المطلوبة

- **`Inquiries` kit** أو امتداد Conversations بـ `IsInquiry`.
- **`Reviews` kit**: `Review { Id, ListingId, AuthorId, Rating(1-5), Body,
  Status, VerifiedPurchase, At }` + events + reply.
- **`Images` kit**: تخزين/CDN/أحجام متعددة. (لا يوجد).
- **`Analytics`**: projection من `ListingViewed` (موجود) لرسوم زمنية.

### تحسينات التصميم (مقابل الحالي)

- **SellerHome**: استبدال بطاقة CTA البسيطة بـ "today panel" (KPIs ٤ +
  "يحتاج انتباهك" + رسم) — يُعطي البائع شعور "أنا أُدير عملاً".
- **Listing card**: إضافة شارات (مميّز/جديد/منخفض المخزون)، شريط حالة،
  إجراء سريع (مفضلة) بدون فتح التفاصيل.
- **معرض صور** في تفاصيل الإعلان.
- **شريط بحث ذكي** بـ autocomplete واقتراحات.

## النمط ٢ — Classifieds (إعلانات مبوّبة)

**أمثلة الإنتاج**: عقار، سيارات مستعملة، وظائف، خدمات.

### الحالة الحالية

- يستخدم نفس قالب SellerHome + التصفّح الافتراضي.
- **مفقود**: ترقية إعلان (boost)، تجديد، انتهاء صلاحية، باقات إعلان مدفوعة،
  بحث متقدم على الخصائص الديناميكية.

### تطبيق الناشر — الشاشات

1. **لوحة الناشر**: عدد الإعلانات النشطة، رصيد الترقيات، أيام متبقية،
   مشاهدات الأسبوع، اتصالات.

2. **نشر إعلان**: wizard مشابه للـ Marketplace + اختيار "نوع النشر"
   (مجاني / مميّز / مُثبَّت) بأسعار مختلفة.

3. **إعلاناتي**: جدول مع حالة + أيام متبقية + زر "تجديد" و "ترقية".

4. **ترقية إعلان**: modal يعرض أنواع الترقية (مميز/مثبت/إعادة نشر) +
   السعر + المدة + الدفع.

5. **إحصاءات إعلان**: مشاهدات يومية، اتصالات، حفظ في المفضلة، نسبة الرد.

### تطبيق الباحث — الشاشات

1. **رئيسية بحث**: بحث + فئات + إعلانات مميزة في الأعلى + أحدث الإعلانات.

2. **نتائج البحث المتقدمة**: فلترة على خصائص ديناميكية حسب الفئة
   (DynamicAttributes موجود — يحتاج UI متقدّم). خريطة جانبية تعرض نتائج
   نقطية. حفظ البحث.

3. **تنبيهات البحث المحفوظ**: عند ظهور إعلان جديد يطابق بحثاً محفوظاً
   (موجود جزئياً، يحتاج إشعار push + إعدادات تكرار).

4. **تفاصيل الإعلان**: مع شارة "مميز" أو "مثبت"، تقييم الناشر (Reviews
   kit جديد)، عرض على الخريطة، تواصل مباشر.

### State machine للإعلان

`draft → pending_review? → published → (expired | paused | sold | deleted)`
- `pending_review` اختياري (إعدادات المتجر: إشراف قبل النشر؟).
- `sold` حالة نهائية للأشياء المباعة (تبقى مرئية كمرجع).

**Boost**: `Listing.Boosts: List<BoostRecord>` — كل boost له `Type, StartsAt,
EndsAt`. الفهرسة عند البحث ترفع الإعلانات النشطة المرقّاة.

### الفجوات النطاقية

- **`Boost`** على Listing + ميكانيكية ترتيب البحث.
- **`Reviews`** للناشرين (نفس Marketplace).
- **`Reports`** (مفصول عن Support): بلاغات تنفصل إلى طابور إشراف.

### تحسينات التصميم

- **Listing card** للإعلانات: شارة الترقية، صورة بارزة، سعر بحجم كبير،
  موقع، تاريخ النشر بشكل نسبي ("قبل ٣ ساعات").
- **خريطة البحث**: split-view (قائمة + خريطة) مثل Bayut/Aqar.
- **autocomplete في البحث** للمناطق والفئات.

## النمط ٣ — Rental (التأجير)

**أمثلة الإنتاج**: تأجير سيارات، شقق مفروشة قصيرة الأمد، معدات.

### الحالة الحالية

- لا workflow حقيقي. لا يوجد مفهوم "التوفر" أو "الحجز" في الكود.
- هذا النمط هو **الأقل جاهزية** ويحتاج بناء نطاق كامل.

### تطبيق المالك — الشاشات

1. **لوحة المالك**: حجوزات قادمة (هذا الأسبوع/الشهر)، إيراد الشهر، أصول
   شاغرة، طلبات حجز جديدة.

2. **إدارة الأصول** (`/me/assets`): قائمة بكل أصل (سيارة/شقة)، حالته
   (متاح/مؤجَّر حالياً/معطّل للصيانة)، ميزات، صور، سعر اليوم/الشهر.

3. **تقويم التوفر** (`/me/calendar`):
   - عرض شهري/أسبوعي لكل الأصول.
   - سحب لإنشاء فترة "غير متاح" (صيانة).
   - عرض الحجوزات المؤكّدة + الطلبات المعلّقة.

4. **طلبات الحجز** (`/me/bookings`):
   - طابور الطلبات الواردة (تاريخ، مدة، عميل، سعر).
   - قبول/رفض/مفاوضة.
   - حجوزات نشطة: تاريخ التسليم/الاستلام، حالة، تأمين.

5. **التسليم/الاستلام**:
   - check-out: تأكيد التسليم + صور حالة الأصل + توقيع رقمي.
   - check-in: عند الإرجاع، تقييم حالة، خصومات/مكافآت تأمين.

6. **التأمين والودائع**: عرض المبالغ المحتجزة، إفراج/خصم.

### تطبيق المستأجر — الشاشات

1. **بحث بالتاريخ**: حقل "من — إلى" + موقع → نتائج الأصول المتاحة فقط.

2. **تفاصيل الأصل**: معرض صور، مواصفات، تقويم توفر مرئي، أسعار حسب
   المدة، تقييمات، شروط (تأمين، حد كيلومترات، …).

3. **حجز**: اختيار التواريخ → ملخّص (السعر + الضرائب + التأمين) → دفع
   → تأكيد.

4. **حجوزاتي** (`/me/rentals`): قائمة (قادمة/نشطة/منتهية) + تفاصيل
   بكل حالة (وثائق التسليم، رمز الاستلام، إلغاء بشروط).

5. **عند بدء الإيجار**: شاشة تسليم تفاعلية مع المالك.

### State machine للحجز

```
inquiry → pending → (confirmed | declined)
confirmed → picked_up → returned → completed
confirmed → cancelled (مع سياسة استرداد)
picked_up → overdue (إن لم يُرجَع في الوقت)
```

### الفجوات النطاقية (الأكبر بين الأنماط)

نطاق **`Rentals` kit** جديد كامل:
- **`RentalAsset`**: مشتق من Listing مع `AssetType`, `DailyRate`,
  `WeeklyRate`, `Deposit`, `MinDays`, `MaxDays`.
- **`Availability`** projection: لكل أصل، الأيام المحجوزة + الأيام المعطّلة.
- **`Booking`**: `Id, AssetId, RenterId, From, To, TotalPrice, Deposit,
  Status, Events: List<BookingEvent>`.
- **events**: BookingRequested, BookingConfirmed, BookingCancelled,
  BookingPickedUp, BookingReturned, DepositReleased.
- **خوارزمية تعارض**: عند طلب حجز جديد، فحص التعارض مع الحجوزات والفترات
  المعطّلة قبل القبول.
- **تكامل دفع**: حجز المبلغ (authorization) عند التأكيد، تحصيل عند التسليم.

### تحسينات التصميم

- **تقويم تفاعلي** مكوّن جديد `<AcBookingCalendar>` — يعرض بصرياً الأيام
  المحجوزة/المتاحة/المعطّلة بألوان مختلفة، يدعم اختيار مدى.
- **معرض صور بانورامي** للأصول (سيارات، شقق).
- **شريط مقارنة سعر** للمدد المختلفة (يوم/أسبوع/شهر).
- **بطاقة "العقد" الرقمية**: تفاصيل، شروط، توقيع، QR.

## النمط ٤ — On-demand / Trip (طلبات حسب الموقع)

**أمثلة الإنتاج**: نقل ركاب، توصيل، خدمات منزلية فورية.

### الحالة الحالية (الأكثر تطوراً نسبياً)

- **RiderHome**: hero "انشر مشواراً" + قائمة طلباتي بالحالة.
- **DriverHome**: stats pills + قائمة المشاوير المتاحة + فلتر بنطاق.
- **Offers kit موجود بالكامل** (Offer, ListingMatch, TripStatus) لكن
  **بلا Server handlers** — كل المنطق في endpoints مباشرة. صعب الاختبار
  والصيانة.

### تطبيق الطالب (Rider) — الشاشات

1. **رئيسية**: hero "اطلب الآن" + طلباتي النشطة + طلباتي السابقة.

2. **نشر طلب**: نموذج (من، إلى، نوع، وقت، ملاحظة، سعر مقترح إن وُجد).
   استخدام GPS لـ "من". خريطة لتحديد "إلى".

3. **استقبال العروض** (real-time): بعد النشر، شاشة "ينتظر العروض" مع:
   - عدّاد العروض الواردة (تحديث live).
   - قائمة العروض: السائق، سعره، تقييمه، مسافته الحالية، ETA.
   - قبول → ListingMatch → فتح شاشة الرحلة.

4. **شاشة الرحلة النشطة**:
   - خريطة مع موقع السائق الحي (مفقود — يحتاج تحديث مواقع SignalR).
   - حالة الرحلة: قادم → وصل → في الرحلة → اكتمل.
   - زر محادثة + اتصال + إلغاء (بشروط).

5. **انتهاء الرحلة**: تقييم السائق، إيصال، دفع (إن وُجد).

6. **سجل الرحلات** + إعادة الطلب من رحلة سابقة.

### تطبيق المزود (Driver) — الشاشات

1. **رئيسية**: حالة العمل (متاح/مشغول/غير متصل)، إحصائيات اليوم (رحلات،
   مكاسب، زمن نشط)، رحلة نشطة إن وُجدت.

2. **استكشاف الطلبات** (`/explore`):
   - feed الطلبات المفتوحة (موجود) + فلترة بنطاق (موجود) + ترتيب
     (الأقرب/الأعلى سعراً/الأحدث).
   - بطاقة طلب: من→إلى على خريطة مصغّرة، سعر، مسافة، عمر الطلب.

3. **تقديم عرض**: من بطاقة الطلب، نموذج (سعر، رسالة، ETA) → submit.

4. **عروضي المعلّقة** (`/me/offers`): قائمة بعروضي، حالة (معلّق/مقبول/مرفوض)،
   انتهاء صلاحية.

5. **رحلة نشطة**:
   - خريطة + موقع الطالب + خط الطريق.
   - أزرار: "أنا في الطريق" / "وصلت" / "بدأت الرحلة" / "أكملت".
   - بث موقعي للطالب (real-time).

6. **حدّد منطقة عملك** (`/me/area`): اختيار مركز ونصف قطر على خريطة
   (موجود جزئياً).

7. **مكاسبي وتقييماتي**.

### State machine

**Offer**: `submitted → (accepted | rejected | withdrawn | expired)`.
**Trip (ListingMatch)**: `active → arrived → in_progress → completed`.
**Trip alternate**: `active → aborted (by_owner | by_offerer)`.

(موجود بالكامل في الكود).

### الفجوات النطاقية

- **`Offers.Server`** — تحويل المنطق من endpoints inline إلى Wolverine
  handlers (`SubmitOffer`, `AcceptOffer`, `RejectOffer`, `WithdrawOffer`,
  `ArriveAtPickup`, `CompleteTrip`, `AbortTrip`).
- **تتبع موقع حي**: SignalR broadcast لـ driver location → rider.
  يحتاج: throttling (كل 3-5 ثوان لا أكثر)، تخزين آخر موقع فقط.
- **Reviews** (مشترك): تقييم driver وrider متبادل.
- **Earnings** للسائق (projection من الرحلات المكتملة).

### تحسينات التصميم

- **خريطة كاملة الشاشة** على شاشة الرحلة (Apple Maps style)، البطاقة
  السفلية sticky تعرض الحالة + الأزرار.
- **رسوم متحركة** على تغيّر الحالة (انتقال "قادم → وصل" بإحساس).
- **Live offers ticker**: العروض تنزل من الأعلى كبطاقات مع رقم زمن live
  (مثل Careem).
- **حالة العمل ظاهرة** كـ pill كبير في الـ top bar للسائق (toggle سريع).

## مَنصَّة الخصائص المشتركة (Cross-cutting)

عوامل تنطبق على كل الأنماط، تُبنى مرة وتُستخدم عبر:

### ١. التقييمات (Reviews) — نطاق جديد إلزامي

```csharp
public sealed class Review {
    Guid Id; Guid TargetUserId; Guid AuthorId; string AuthorName;
    int Rating; // 1-5
    string Body;
    string Context; // "rental" | "trip" | "marketplace"
    Guid? ContextEntityId; // listing/booking/match
    bool VerifiedTransaction;
    DateTime At;
}
```
Projection للمتوسط + العدد على User. UI: نجوم + شارة "موثّق" + رد المالك.

### ٢. الصور والإعلام (Media) — نطاق جديد إلزامي

- تخزين (Azure Blob/S3/Local) — منفذ مجرّد.
- multiple-sizes: thumb (200), card (600), full (1600).
- معرض صور `<AcGallery>`، lazy load، lightbox.

### ٣. المدفوعات (Payments) — يفعّل كل المعاملات

- بوابة (Moyasar/Tap) + webhook + idempotency.
- نطاق `Payments` kit: `PaymentIntent, Payment, Refund, Payout`.
- ربط بـ Subscription (طبقة ٢) + المعاملات داخل التطبيقات (طبقة ٤).

### ٤. الإشعارات السياقية (per-role)

لكل دور، إشعارات مختلفة:
- Rider: عرض جديد، السائق وصل، السائق ألغى.
- Driver: قُبل عرضك، الرحلة لُغيَت، رحلة جديدة قريبة.
- Vendor: استفسار جديد، إعلان على وشك الانتهاء، تقييم جديد.
- Renter: طلب الحجز قُبل، وقت التسليم اقترب.
- إلخ.

كل إشعار يدعم: in-app، web push (موجود)، email/SMS (مع تفضيلات).

### ٥. Onboarding خاص بكل دور

- بعد اختيار الدور، صفحة `/me/role/onboarding` (موجودة) تجمع RoleField
  المطلوبة فقط. تظهر تدريجياً (لا نطلب license_number من السائق قبل
  أن يحاول تقديم عرض).
- مكوّن `<AcRoleFieldsForm>` يعرض الحقول بناءً على `RoleField.Type`.

### ٦. الـ PWA per role (موجود) + صقل

- PWA install banner مخصّص لكل دور (موجود).
- offline.html بحالات مفيدة (لا "أنت غير متصل" فقط، بل "تصفّحت سابقاً
  هذه الإعلانات، إليك نسخة مخبأة").

### ٧. الـ a11y وi18n

- كل النصوص عبر `L["key"]` (Law 7 في CLAUDE.md). نراجع لوحات Studio
  الجديدة (بعضها hardcoded عربي).
- RTL/LTR صحيح في كل المكوّنات.
- contrast 4.5:1 minimum، تنقل لوحة مفاتيح، ARIA labels.

## مَلحوظات على القَوالِب الحاليَّة في `RoleCatalog`

١. **`tenant_admin`** ليس دوراً للمستخدم النهائي — هو دور إداري داخل
   المتجر. يجب فصله عن الأدوار "التطبيقات" بصرياً في picker (`RoleLanding`
   يستثنيه — جيد). للدخول الإداري يجب توجيهه للوحة عمليات التطبيق (طبقة ٣).

٢. **`customer`** له صلاحيات قليلة (browse, offer.submit, chat.start) —
   مناسب لـ Marketplace والـ Trip. لكن في Classifieds الباحث يحتاج
   "favorite, save_search" فقط، لا offer.submit. **اقترح**: تخصيص
   صلاحيات customer حسب نمط المتجر، أو فصل `searcher` و `buyer` و `rider`.

٣. **حقول الأدوار الحاليَّة قليلة**:
   - `driver`: vehicle_type, vehicle_plate, license_number ✓ كافٍ.
   - `vendor`: business_name, business_type — يحتاج: CR/سجل تجاري، VAT،
     bank account للتسوية.
   - `host`: contact_phone فقط — يحتاج: ID، صور هوية، عنوان.

   تطوير `RoleCatalog` ليشمل **حقول KYC** فعلية ضرورية لكل دور قبل بدء
   المعاملات المالية.

٤. **`Role.HomeRoute`** موجود لكن غير مُستثمر — يستخدمه `PostLoginRouteAsync`
   فقط. يجب توسيعه لتحديد **شريط تنقّل الدور** (الـ bottom nav items) —
   كل دور له شريط مخصّص، لا قائمة عامة.

## القَرارات المَطلوبَة (إضافَة لِلخُطَّة الرَّئيسيَّة)

١. **التَّقييمات أُحاديَّة أم ثُنائيَّة؟** (هل السائق يُقَيِّم الراكِب
   أَيضاً؟ تُؤَثِّر على نَموذَج Reviews kit.)

٣. **التَّحَقُّق مِن الهُويَّة (KYC)**: هَل نَدمُج Nafath لِلتَحَقُّق
   مِن البائِعين/السائِقين قَبل بَدء المُعامَلات؟

٤. **Live tracking**: ضَروريّ لِـ On-demand مِن البِدايَة، أَم نُؤَجِّله؟

٥. **Rental scope**: نَبني الـ Bookings kit الآن، أَم نُؤَجِّل الـ Rental
   لِما بَعد إطلاق Marketplace/Trip؟
