# خطة الإنتاج — منصة ACommerce (نسخة قابلة للإطلاق الفعلي)

> هذه ليست خطة إثبات مفهوم. الهدف: بعد تنفيذها يمكن إطلاق المنصة فعلياً
> لعملاء يدفعون. كل طبقة تُعالَج بجدية بيئة الإنتاج: صلاحيات، تدقيق،
> موثوقية، أداء، وتجربة احترافية.

## الوضع الحالي (خط الأساس)

ما هو موجود فعلاً (لا نعيد بناءه، نطوّره):
- **النطاقات (kits)**: Listings, Offers (مشاوير/عروض), Chat, Support (تذاكر),
  Subscriptions (باقات), Notifications, Auth, Roles + RoleCatalog (٨ قوالب),
  Tenants, Favorites, Profiles, SavedSearches, Maps, Realtime (SignalR).
- **لوحات Studio (رائد الأعمال)**: StudioHome, StudioApp, StudioAppConsole
  (للقراءة فقط)، صفحات تهيئة (Branding/Categories/Roles/Regions)، StudioStudy
  (تحليل + heatmap + refine + تصدير)، StudioBilling.
- **لوحات Admin (المنصة)**: AdminHome (gated)، QualityMonitor، Fixtures،
  صفحات Tenant، AgentChat.
- **تطبيقات الأدوار**: RiderHome, DriverHome, SellerHome, RoleLanding.

الفجوات الإنتاجية الكبرى المرصودة:
1. **StudioAppConsole للقراءة فقط** — لا إدارة عروض، لا رد على تذاكر، لا
   إشراف على إعلانات، لا إدارة مستخدمين فعلية، لا تحليلات إيراد.
2. **لا سجل تدقيق (audit log)** لأي عملية إدارية.
3. **لا صلاحيات فعلية على الـ Studio** — أي مالك يرى لوحته، لكن لا فريق/أعضاء.
4. **لا تكامل دفع حقيقي** (الباقات نية فقط).
5. **OTP وهمي** (123456) و **SMS وهمي** — لا مزود إنتاج.
6. **تطبيقات الأدوار بدائية** — بطاقات بسيطة، لا workflow كامل لكل دور.
7. **لا اختبارات تكامل** ولا CI gate.

## الطبقة ١ — لوحة تحكم مشرف المنصة (`/admin`)

**الدور**: مالك المنصة (أنت) يدير المستأجرين، يراقب الصحة، يتدخل في النزاعات،
يدير الفوترة على مستوى المنصة، ويضبط إعدادات النظام.

### ١.١ نموذج الصلاحيات (أساس كل شيء)
- استبدال `IsPlatformAdmin` (bool) بـ **أدوار منصة دقيقة**:
  `platform_owner` (كل شيء)، `platform_support` (تذاكر + قراءة)،
  `platform_billing` (فوترة فقط)، `platform_analyst` (قراءة فقط).
- كيان جديد `PlatformStaff { UserId, Role, GrantedBy, GrantedAt }`.
- `PlatformAuthFilter` (EndpointFilter) + `<RequirePlatformRole Role="...">`
  بدلاً من `<RequirePlatformAdmin>` العام.

### ١.٢ سجل التدقيق (Audit Log) — إلزامي للإنتاج
- كيان `AuditEntry { Id, ActorId, ActorName, Action, EntityType, EntityId,
  TenantSlug?, Before?, After?, Ip, At }`.
- `IAuditWriter` يُحقَن في كل endpoint إداري؛ يكتب قبل/بعد كل تغيير.
- صفحة `/admin/audit` بفلترة (الفاعل، النوع، المستأجر، المدى الزمني).

### ١.٣ لوحات المراقبة (تطوير QualityMonitor الحالي)
- **صحة النظام**: حالة DB، حالة Wolverine queue، آخر الأخطاء، زمن الاستجابة.
- **مالية المنصة**: MRR، عدد المشتركين لكل باقة، الإيراد المتوقع، churn.
- **استخدام الحاضنة**: (موجود) + تكلفة LLM التراكمية + متوسط زمن التحليل.
- **النمو**: مستخدمون جدد/أسبوع، تطبيقات مُطلقة، معدل التحويل بالمراحل.

### ١.٤ إدارة المستأجرين (تطوير AdminHome)
- جدول احترافي بفلترة/بحث/ترتيب/ترقيم (بدل شبكة البطاقات).
- إجراءات لكل مستأجر: تعليق/تفعيل، حذف ناعم، عرض كـ (impersonate آمن)،
  تصدير بيانات (GDPR/نَقل)، تغيير الباقة يدوياً.
- صفحة تفصيل مستأجر: نشاط، مالك، فريق، استهلاك، تذاكر مرتبطة، سجل تدقيق.

### ١.٥ مركز النزاعات والإشراف
- طابور بلاغات الإعلانات على مستوى المنصة (من Support tickets بنوع report).
- إجراءات الإشراف: إخفاء إعلان، حظر مستخدم، إغلاق تذكرة مع سبب.

### ١.٦ إعدادات المنصة
- مفاتيح المزودين (LLM, SMS, Payment) — تُقرأ من secrets، تُعرض حالتها فقط.
- إصدارات الـ prompt + A/B (موجود جزئياً في PromptVersion) — واجهة تبديل.
- بنود قانونية (ToS/Privacy) مع إصدار — يُجبر القبول عند التغيير.

### قابلية الإطلاق للطبقة ١
صلاحيات دقيقة + سجل تدقيق كامل + impersonation آمن + تعليق مستأجر + مراقبة
صحة حية. **بدون هذه لا يُطلق admin للإنتاج.**

## الطبقة ٢ — لوحة تحكم رائد الأعمال (`/studio`)

**الدور**: صاحب الأفكار/التطبيقات. مثل لوحة اشتراك في متجر تطبيقات: يدير
حسابه، فريقه، فوترته، ويتنقل بين تطبيقاته.

### ٢.١ الحساب والفريق (متعدد المستخدمين)
- حالياً مالك واحد. للإنتاج: `AppMembership { TenantSlug, UserId, StudioRole,
  InvitedBy, At }` بأدوار: `owner`, `manager`, `support`, `viewer`.
- دعوة عضو بالبريد/الهاتف + قبول + سحب صلاحية.
- كل صفحات `/studio/apps/{slug}/*` تفحص العضوية لا الملكية فقط.

### ٢.٢ الفوترة الحقيقية
- تكامل **Moyasar/Tap** (بوابة سعودية): اشتراك متكرر، فاتورة ZATCA، تجديد
  تلقائي، فشل الدفع → تعليق ناعم.
- كيان `Invoice` + `PaymentMethod` + webhook handler.
- صفحة `/studio/billing` تعرض الاشتراك الفعلي، الفواتير، طريقة الدفع.

### ٢.٣ نظرة شاملة على المحفظة
- StudioHome يطوَّر إلى لوحة محفظة: لكل تطبيق KPI سريع (مستخدمون نشطون،
  إعلانات، إيراد إن وُجد، تنبيهات تحتاج تدخل).
- "يحتاج انتباهك": تذاكر مفتوحة، عروض معلقة، إعلانات مبلّغ عنها — عبر كل التطبيقات.

### ٢.٤ الأمان والإشعارات
- سجل دخول، أجهزة، خروج عن بُعد.
- تفضيلات إشعار رائد الأعمال (بريد/SMS/push) لأحداث تطبيقاته.

### قابلية الإطلاق للطبقة ٢
فريق + أدوار + دفع متكرر فعلي + فواتير ZATCA. **الدفع الفعلي هو البوابة
الحرجة للإطلاق التجاري.**

## الطبقة ٣ — لوحة تحكم التطبيق (`/studio/apps/{slug}`)

**الدور**: قلب التشغيل اليومي. هنا تكمن أكبر فجوة حالياً (Console للقراءة فقط).
يجب أن تصبح مركز عمليات كامل، **يتكيّف حسب نوع التطبيق (النمط/الأدوار)**.

### ٣.١ بنية موحّدة (تبويبات مركز العمليات)
شريط جانبي ثانوي داخل التطبيق:
`نظرة عامة · المستخدمون · الإعلانات · العروض · المحادثات · التذاكر ·
الإشعارات · الباقات · سجل العمليات · الإعدادات`

كل تبويب يظهر **فقط إن كان نمط التطبيق يستخدمه** (تطبيق إعلانات بلا عروض
يخفي تبويب العروض).

### ٣.٢ التبويبات التفصيلية (CRUD حقيقي، ليس عدّادات)

**نظرة عامة**: KPIs + رسوم زمنية (إعلانات/يوم، رسائل/يوم) + "يحتاج تدخل".

**المستخدمون**: جدول بفلترة/بحث، تفاصيل المستخدم (دوره، نشاطه، إعلاناته،
تذاكره)، إجراءات: منح/سحب دور، تعليق، إعادة تعيين. يستبدل التفويض الحالي لـ
`/admin/tenants/{slug}/users`.

**الإعلانات** (إشراف): جدول كل الإعلانات، حالة (نشط/محذوف/مبلّغ)، معاينة،
إخفاء/استرجاع، حذف، تمييز، عرض المالك. — *غير موجود حالياً.*

**العروض** (للأنماط ذات العروض): طابور العروض المعلّقة، المطابقات النشطة
(ListingMatch/TripStatus)، تدخل في النزاعات، إلغاء مطابقة عالقة، سجل الرحلات
المكتملة/الملغاة. — *غير موجود حالياً، رغم وجود كامل نطاق Offers.*

**المحادثات** (إشراف): قائمة المحادثات، فتح محادثة للقراءة (للنزاعات)،
إغلاق/تجميد محادثة مسيئة. للخصوصية: سجل وصول مدقّق.

**التذاكر** (دعم فني كامل): قائمة + فلترة بالحالة، **فتح تذكرة والرد عليها**
(Reply UI)، إغلاق بسبب، تعيين لعضو فريق، SLA/زمن أول رد. — *الرد غير موجود
حالياً رغم وجود TicketReplied.*

**الإشعارات**: بث إشعار للمستخدمين (شريحة/الكل)، سجل المُرسَل، قوالب.

**الباقات** (لمتجر يبيع اشتراكات لمستخدميه): CRUD على Plan، تفعيل/تعطيل،
عرض المشتركين، الإيراد.

**سجل العمليات**: audit log خاص بالتطبيق (من سجل المنصة مُفلتَر بالـ slug).

**الإعدادات**: روابط لصفحات التهيئة الحالية (Branding/Categories/Roles/Regions/
Attributes/PWA) — موجودة، تُدمج كتبويب.

### ٣.٣ الأساس التقني المطلوب
- **خوادم (Server) لـ Offers**: النطاق Core-only حالياً. نضيف
  `ACommerce.Kit.Offers.Server` بـ Wolverine handlers (قبول/رفض/مطابقة/إلغاء)
  + endpoints إشراف.
- **Reply UI للتذاكر**: استخدام `ReplyTicket` command الموجود + endpoint +
  مكوّن محادثة تذكرة.
- **إشراف الإعلانات**: endpoints (hide/restore/delete) فوق `DeleteListing`
  الموجود + علم `IsHiddenByModerator`.
- كل إجراء إشراف يكتب في **audit log** (الطبقة ١.٢).

### قابلية الإطلاق للطبقة ٣
عروض + تذاكر (رد) + إشراف إعلانات + إدارة مستخدمين فعلية، كلها بـ audit،
متكيّفة حسب نمط التطبيق. **هذه أكبر كتلة عمل وأهمها للتشغيل اليومي.**

## الطبقة ٤ — القوالب والأدوار كتطبيقات فرعية مضمّنة

**الدور**: كل دور = تطبيق مستقل للمستخدم النهائي. حالياً (RiderHome/DriverHome/
SellerHome) بطاقات بسيطة. للإنتاج تحتاج workflow كامل + تصميم احترافي.

### ٤.١ القوالب الأربعة كحُزم متكاملة
لكل نمط، نعرّف **حزمة تطبيق** كاملة (صفحات + workflow + حالات):

**أ) Marketplace (متجر متعدد البائعين)**
- المشتري: تصفح → تفاصيل → محادثة/طلب → دفع (مستقبلاً) → تقييم.
- البائع: لوحة إعلاناتي (نشط/مسودة/منتهي) + تحليلات (مشاهدات/تحويل) +
  محادثات + طلبات + باقة.

**ب) Classifieds (إعلانات مبوّبة)**
- الناشر: نشر/تجديد/ترقية إعلان + إحصاءات.
- الباحث: بحث متقدم + بحوث محفوظة + تنبيهات + مفضلة.

**ج) Rental (تأجير)**
- المالك: إدارة الأصول + التقويم/التوفر + طلبات الحجز + الإرجاع/التأمين.
- المستأجر: بحث بالتوفر + حجز + سجل الإيجارات.
- **ناقص جوهري**: لا يوجد نطاق Availability/Booking — يحتاج بناء.

**د) On-demand / Trip (طلبات حسب الموقع)**
- الطالب (rider): نشر طلب → استقبال عروض → اختيار → تتبع → إنهاء → تقييم.
- المزود (driver): استكشاف الطلبات القريبة → تقديم عرض → قبول → وصول →
  إكمال. (نطاق Offers موجود، يحتاج صقل UX + تتبّع حي على الخريطة.)

### ٤.٢ التحسينات المشتركة لكل الأدوار
- **تصميم احترافي**: استبدال البطاقات البدائية بـ Role Home حديثة (هيرو
  سياقي + KPIs + إجراء أساسي بارز + خلاصة نشاط حية).
- **حالات فارغة/تحميل/خطأ** مصمّمة لكل صفحة (لا شاشات فارغة).
- **onboarding لكل دور**: جمع الحقول المطلوبة (RoleField موجود) بتدفّق سلس.
- **تقييمات/سمعة**: نطاق `Reviews` جديد (مفقود تماماً، ضروري للثقة في
  marketplace/rental/trip).
- **دفع داخل التطبيق**: ربط Listings/Offers ببوابة الدفع للمعاملات الفعلية.

### ٤.٣ نظام التصميم (احترافية موحّدة)
- توسيع `studio.css` إلى نظام تصميم كامل: tokens + مكوّنات (جدول بيانات،
  drawer، tabs، toast، modal تأكيد، شارات حالة، رسوم بسيطة).
- مكوّن `<AcDataTable>` موحّد (فلترة/ترتيب/ترقيم/إجراءات صف) يُعاد استخدامه
  في كل لوحات الطبقات ١-٣.
- RTL + بايلنغوال (L) كامل عبر كل اللوحات الجديدة.

### قابلية الإطلاق للطبقة ٤
كل نمط له حزمة تطبيق كاملة بحالات وworkflow وتصميم احترافي + تقييمات +
(لاحقاً) دفع. **Rental يحتاج نطاق حجز جديد؛ البقية صقل وبناء صفحات.**

## المتطلبات الشاملة للإنتاج (تقطع كل الطبقات)

هذه ليست طبقة، بل شروط إطلاق إلزامية:

1. **الهوية والأمان**: استبدال OTP الوهمي بمزود SMS فعلي (Unifonic/Taqnyat)؛
   تقوية الجلسات (تدوير token، إبطال، انتهاء)؛ rate limiting على auth.
2. **سجل التدقيق** عبر كل عملية إدارية (الطبقة ١.٢) — غير قابل للتفاوض.
3. **الدفع**: بوابة سعودية فعلية + فواتير ZATCA + webhooks + تسوية.
4. **حماية البيانات**: عزل المستأجرين (موجود عبر conjoined tenancy، يُراجَع)؛
   تصدير/حذف بيانات المستخدم (PDPL السعودي)؛ تشفير الأسرار.
5. **الموثوقية**: ترحيلات DB مُدارة؛ نسخ احتياطي؛ صحة/جاهزية endpoints؛
   معالجة أخطاء موحّدة + صفحات خطأ؛ مراقبة (OpenTelemetry موجود في Wolverine).
6. **الأداء**: فهرسة Marten للاستعلامات الثقيلة؛ projections للوحات بدل
   التجميع في الذاكرة (QualityMonitor/Console يجمعان في الذاكرة الآن).
7. **الاختبارات**: integration tests لكل workflow حرج (auth, analysis, build,
   offer accept, ticket reply, payment)؛ CI gate قبل الدمج.
8. **i18n**: مراجعة كل النصوص عبر L (بعض اللوحات الجديدة hardcoded عربي).
9. **إمكانية الوصول (a11y)**: تباين، تنقل لوحة مفاتيح، ARIA على الجداول.

## ترتيب التنفيذ المقترح (مراحل قابلة للشحن)

كل مرحلة تنتهي بحالة قابلة للإطلاق التدريجي:

**م١ — الأساس المشترك** (يفتح كل شيء بعده)
نظام التصميم + `<AcDataTable>` + سجل التدقيق + صلاحيات دقيقة (منصة + studio team).

**م٢ — مركز عمليات التطبيق (الطبقة ٣)** — أعلى قيمة تشغيلية
Offers.Server + إدارة عروض + Reply تذاكر + إشراف إعلانات + إدارة مستخدمين.

**م٣ — admin إنتاجي (الطبقة ١)**
جدول مستأجرين + تعليق/impersonation + مركز نزاعات + مراقبة صحة + مالية.

**م٤ — الفوترة الفعلية (الطبقة ٢)**
بوابة دفع + اشتراك متكرر + فواتير ZATCA + فريق رائد الأعمال.

**م٥ — تطبيقات الأدوار (الطبقة ٤)**
صقل الأنماط الأربعة + Reviews + onboarding + (Rental: نطاق الحجز).

**م٦ — تصليب الإنتاج**
SMS فعلي + projections + اختبارات + a11y + i18n + نسخ احتياطي + إطلاق.

## القرارات المطلوبة منك قبل البدء

1. **بوابة الدفع**: Moyasar أم Tap أم HyperPay؟ (يؤثر على م٤)
2. **مزود SMS**: Unifonic أم Taqnyat؟
3. **نموذج الإيراد**: اشتراك رائد الأعمال فقط، أم عمولة على معاملات تطبيقاته أيضاً؟
4. **أولوية الأنماط**: أي نمط (marketplace/classifieds/rental/trip) هو أول
   عميل حقيقي مستهدف؟ نصقله أولاً.
5. **Rental**: هل نبني نطاق الحجز/التوفر الآن أم نؤجّله لما بعد الإطلاق الأول؟
